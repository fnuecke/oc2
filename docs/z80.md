# Z80 Machine

This document describes the hardware a Z80 computer presents to the software running on it. It aims to enable writing
a system, reading disks without CP/M, or controlling devices from Z80 code. For CP/M itself and Z80 programming in
general, please refer to existing documentation elsewhere on the web on those.

Device registers are described in [mlapi.md](mlapi.md), [floppy.md](floppy.md) and [serial.md](serial.md).
The sources of the stock boot ROM and the CP/M BIOS can be found in [sedna-cpm](https://github.com/fnuecke/sedna-cpm).

## Overview

- A single Z80 core. The clock is the server setting `vm.z80CycleBudgetPerSecond`, 4M T-states per second by default.
- 64 KiB of address space, no banking, no MMU at the time of writing (see #314).
- 256 I/O ports. All devices are port-mapped, there are no memory-mapped devices.
- The enumeration window at `0xE0` is the only fixed port range. All other devices can be discovered through that.
- 32 interrupt lines into one controller, delivered as maskable interrupts.

## Memory

Memory modules are mapped from `0x0000` upwards. Only the first 64 KiB are visible, so with the default module sizes a
single module covers the whole address space. Modules that do not fit into the remaining space are ignored. Reads from
addresses not backed by memory return `0xFF`, writes to them are ignored.

The boot ROM is a copy of the installed flash memory's contents, 8 KiB in size. It is copied each time the computer
starts. A blank or missing flash memory results in a ROM filled with zeros. While the ROM is mapped, it shadows
`0x0000`-`0x1FFF`: reads return ROM bytes, writes are ignored. The shadowed RAM range is not accessible until the ROM is
unmapped.

A latch device (class `0x07`, name `BOOTRM`) maps and unmaps the ROM. It has a single port. Bit 0 of its value is set
while the ROM is mapped. Writing a value with bit 0 cleared unmaps the ROM, writing one with bit 0 set maps it again.
Other bits are ignored. A reset maps the ROM again.

## Reset State

Power-on and reset are identical.

| State                                          | Value    |
|------------------------------------------------|----------|
| `PC`                                           | `0x0000` |
| `SP`                                           | `0xFFFF` |
| `A`, `F`                                       | `0xFF`   |
| `BC`, `DE`, `HL`, `IX`, `IY`, shadow registers | `0x0000` |
| `I`, `R`                                       | `0x00`   |
| `IFF1`, `IFF2`                                 | cleared  |
| Interrupt mode                                 | 0        |
| Boot ROM                                       | mapped   |
| Interrupt lines                                | all low  |

Devices are reset as well. In particular, a mid-level API call in progress is discarded.

`HALT` with interrupts disabled turns the computer off.

## I/O Ports

- Ports are decoded using the low 8 bits of the port address, the upper 8 bits are ignored. This means the value of `B`
  does not matter for `IN r,(C)` and `OUT (C),r`.
- Reads from unallocated ports return `0xFF`, writes are ignored.
- Port `0xFF` is never allocated. As such, `0xFF` means "no port" in the enumeration window.
- `0xE0`-`0xEF` is the enumeration window.

All other ports are allocated first-fit from `0x00` upwards, each time the computer starts. Port assignments may differ
between starts, computers and worlds, never hardcode them.

## Enumeration Window

The window is sixteen ports at `0xE0`. The main usage pattern is to select an entry, then read its fields. The names
match the constants in [`DEVLIB.INC`](https://github.com/fnuecke/sedna-cpm/blob/main/src/main/asm/devlib.inc), which is
also on the CP/M boot floppy. It's the primary mechanism used to enable dynamic device configuration on machines.

| Port          | Name   | Read                                     | Write                                 |
|---------------|--------|------------------------------------------|---------------------------------------|
| `0xE0`        | `BVER` | Format version, `1`                      | -                                     |
| `0xE1`        | `BCNT` | Number of entries, at most 254           | -                                     |
| `0xE2`        | `BSEL` | Selected entry                           | Selects an entry, rewinds name and id |
| `0xE3`        | `BCLS` | Class                                    | -                                     |
| `0xE4`        | `BATT` | Attributes, depend on the class          | -                                     |
| `0xE5`        | `BPRT` | First port of the device, `0xFF` if none | -                                     |
| `0xE6`        | `BINT` | Interrupt vector, `0xFF` if none         | -                                     |
| `0xE7`        | `BNAM` | Next byte of the names                   | Any value rewinds                     |
| `0xE8`        | `BID`  | Next byte of the id, `0` at the end      | Any value rewinds                     |
| `0xE9`-`0xEF` |        | `0`                                      | -                                     |

Reading `BCNT` or writing `BSEL` updates the list, so it includes devices added or removed since, and rewinds name and
id. Selecting an entry past the end reads class `0x00`, attributes `0`, port `0xFF`, vector `0xFF` and empty names and
id. The reserved registers read `0`, which tells the window apart from unallocated ports.

An entry can have several names. Each name is terminated by a `0`, an empty name marks the end of the list. The first
name is the device **type**, e.g. `UART` or `REDSTN`. Names are not unique. Mid-level API devices have further names,
such as labels set on bus interfaces.
Use [`DEVFIND`](https://github.com/fnuecke/sedna-cpm/blob/main/src/main/asm/devlib.inc) for convenience to look up a
device by any of its names.

Names and ids are printable ASCII. Ids are informational and may be empty. For mid-level API devices, the id is a UUID.

### Classes

| Class  | Meaning              | First name  | Attributes                                                                                       |
|--------|----------------------|-------------|--------------------------------------------------------------------------------------------------|
| `0x00` | Unknown              |             |                                                                                                  |
| `0x01` | Bus                  | `SEDBUS`    | `0`                                                                                              |
| `0x02` | Character device     | `UART`      | `0`                                                                                              |
| `0x03` | Block device         | `FLOPPY`    | Low nibble: unit on the controller. High nibble: media type, see [floppy.md](floppy.md#geometry) |
| `0x04` | Real-time clock      |             |                                                                                                  |
| `0x05` | GPIO                 |             |                                                                                                  |
| `0x06` | Screen               |             |                                                                                                  |
| `0x07` | Boot ROM latch       | `BOOTRM`    | `0`                                                                                              |
| `0x80` | Mid-level API device | Device name | Index to write to [`OCSEL`](mlapi.md#registers)                                                  |

Classes below `0x80` are defined by the emulator, `0x80` and up by the mod. `0x04`-`0x06` are placeholders.

### Order

Entry 0 is the window itself, followed by devices in the order they were added: boot ROM latch, console serial port,
mid-level API devices, native hardware such as disk drives and serial interface cards. This means the console is always
the first class `0x02` entry. The order of installed hardware depends on load order. Identify devices by class, name and
attributes.

### Example

A computer with a redstone interface and a disk drive attached, and a serial interface card installed. Actual port
numbers depend on the installed hardware.

| Ports         | Device                |
|---------------|-----------------------|
| `0x00`        | Boot ROM latch        |
| `0x01`-`0x08` | Console serial port   |
| `0x09`-`0x10` | Mid-level API device  |
| `0x11`-`0x15` | Floppy controller     |
| `0x16`-`0x1D` | Serial interface card |
| `0xE0`-`0xEF` | Enumeration window    |

The window will list the following:

| Entry | `BCLS` | `BATT` | `BPRT` | `BINT` | First name |
|-------|--------|--------|--------|--------|------------|
| 0     | `0x01` | `0`    | `0xE0` | `0xFF` | `SEDBUS`   |
| 1     | `0x07` | `0`    | `0x00` | `0xFF` | `BOOTRM`   |
| 2     | `0x02` | `0`    | `0x01` | `0xFF` | `UART`     |
| 3     | `0x80` | `0`    | `0x09` | `0x02` | `SYSTEM`   |
| 4     | `0x80` | `1`    | `0x09` | `0x02` | `REDSTN`   |
| 5     | `0x80` | `2`    | `0x09` | `0x02` | `SERIAL`   |
| 6     | `0x03` | `0`    | `0x11` | `0xFF` | `FLOPPY`   |
| 7     | `0x02` | `0`    | `0x16` | `0x3E` | `UART`     |

The serial interface card has two entries: its UART registers, and a MLAPI device. Entries 3 to 5 share port `0x09`, the
MLAPI device. To address one of them, write its `BATT` to [`OCSEL`](mlapi.md#registers). `SYSTEM` is always index 0, the
order of the other MLAPI devices is arbitrary.

## Boot

The stock boot ROM ([`bootrom.asm`](https://github.com/fnuecke/sedna-cpm/blob/main/src/main/asm/bootrom.asm)) does the
following:

1. `DI`, sets `SP` to `0xE000`. Finds the console, the first class `0x02` entry.
2. Walks the class `0x03` entries in enumeration order. For each, selects its unit, skips it if the drive is not ready,
   then reads track 0, sector 1.
3. Checks the boot descriptor in that sector. If it is valid, reads the system image and jumps to it.
4. If no drive boots, prints `NO SYSTEM DISK` on the console once and scans again. This way inserting a disk boots
   without a reset.

The ROM keeps its variables at `0xC000`-`0xC00F` and the descriptor at `0xC080`-`0xC0FF`. Both are in use while
loading. It also uses a few bytes of stack below `0xE000`. The system image must not overlap these, nor the shadowed
range below `0x2000`.

### Boot Descriptor

The boot descriptor is stored in the first 8 bytes of track 0, sector 1. Words are little-endian.

| Offset | Size | Content                                                             |
|--------|------|---------------------------------------------------------------------|
| 0      | 2    | Magic, `'S'`, `'B'`                                                 |
| 2      | 2    | Load address                                                        |
| 4      | 2    | Entry address                                                       |
| 6      | 1    | Number of sectors to load, not zero. At most 255, i.e. 32,640 bytes |
| 7      | 1    | Sectors per track, not zero                                         |

The image is read from the sectors following the descriptor, starting at linear index 1, 128 bytes each, to consecutive
addresses starting at the load address. Linear index `n` is track `n / spt`, sector `n % spt + 1`. If a read fails, the
drive is skipped.

On entry:

- `C` is the first port of the disk controller booted from, `B` is its unit. Each disk controller in the mod has a
  single drive, so `B` is always `0`.
- Interrupts are disabled, interrupt mode is 0.
- The ROM is still mapped. The system unmaps it using the latch, once it no longer runs code from it.
- `SP` is inside the ROM's stack. Set your own.

A custom ROM starts in the reset state described above, and can do anything from there. The ROM image and the boot
floppy can be replaced using a data pack, see [Block Devices](datapack.md#block-devices). Files for the CP/M floppy are
covered in [CP/M Files](datapack.md#cpm-files).

### CP/M Startup

The shipped floppy begins with the descriptor, followed by the CCP at `0xE200`, the BDOS at `0xEA00` and the BIOS at
`0xF800`. It is loaded to `0xE200`, the entry is at `0xF800`.
The BIOS ([`cbios.asm`](https://github.com/fnuecke/sedna-cpm/blob/main/src/main/asm/cbios.asm)) then:

1. Stores the boot port and unit.
2. Finds the latch (class `0x07`), the console (first class `0x02`) and an optional serial interface card (second class
   `0x02`). If latch or console are missing, it executes `DI`, `HALT`.
3. Assigns up to four class `0x03` entries to drives `A:`-`D:` in enumeration order,
   then swaps the boot drive into `A:`.
4. Writes `0` to the latch, installs the jumps at `0x0000` and `0x0005`, and enters the CCP.

A warm boot reads CCP and BDOS from the boot drive again. CP/M never enables interrupts.

## Interrupts

The core implements interrupt modes 0, 1 and 2, as well as the non-maskable interrupt.

- A total of 32 lines. Line 0 is never assigned, devices use lines 1 to 31.
- The vector for line `n` is `n << 1`, i.e. `0x02`-`0x3E`. As such, vectors are even and in mode 2 each line uses one
  word of the table at `I << 8`, where `I` is the interrupt vector register.
- Interrupts are level-triggered. A line stays raised until the device lowers it, clear it in the device before `EI`.
- If several lines are raised, the lowest line number is delivered first.
- Mode 1: `RST 0x38`, i.e. pushes `PC` and jumps to `0x0038`.
- Mode 0: executes the vector if it is an `RST` opcode, `RST 0x38` otherwise. The interrupt controller provides vectors
  for mode 2, which are never `RST` opcodes, so this behaves like mode 1.
- Mode 2: pushes `PC` and jumps to the address stored at `(I << 8) | vector`.
- Non-maskable: jumps to `0x0066`. Currently no device raises it.

| Device                | Interrupt                                                                                                                               |
|-----------------------|-----------------------------------------------------------------------------------------------------------------------------------------|
| Serial interface card | The highest free line, assigned when the computer starts. Reported in `BINT`. Raised according to the UART's interrupt enable register. |
| Console serial port   | None, `BINT` is `0xFF`. Poll the line status register.                                                                                  |
| Floppy controller     | None. Poll the busy bit in the status register, also see the lost data timeout in [floppy.md](floppy.md#commands).                      |
| Mid-level API         | Line 1, vector `0x02`, reported in `BINT`. Raised while events are queued and enabled, see [mlapi.md](mlapi.md#events).                 |
| Window, latch         | None.                                                                                                                                   |
